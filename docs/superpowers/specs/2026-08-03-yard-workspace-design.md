# 庭院切换与庭院管理设计规格

日期：2026-08-03  
状态：已完成交互讨论，待用户审阅书面规格

## 1. 背景

当前庭院 IoT App 原型已经具备设备、场景、定时、联动和“我的”四个主 Tab，并支持深色版和暖白版两套视觉。现有数据仍以单一庭院为中心，顶部“我的庭院”尚未形成完整的切换、创建、加入和管理流程。

本次设计把“庭院”升级为独立工作空间。用户切换庭院时，设备、区域、场景、定时、联动、时区和权限整体切换，避免不同庭院之间的数据和操作状态相互污染。

## 2. 目标

- 完成庭院选择、切换、新建、加入和管理流程。
- 为所有者、普通成员、临时安装商提供不同的可见内容和操作权限。
- 保证每个庭院的设备、区域、场景、自动化和时区完全独立。
- 深色版和暖白版共用业务数据与交互规则，但分别实现页面视觉。
- 通过三个预置庭院展示不同角色和数据规模下的完整原型体验。

## 3. 非目标

- 本阶段不讨论或实现真实硬件协议、云端接口和账号体系。
- 不实现庭院删除、所有权转让和高级组织架构。
- 不实现庭院平面图。
- 新建庭院流程不包含邀请成员和添加首个设备；这些操作在创建完成后通过独立入口完成。
- 不自动为新庭院生成示例设备、场景或自动化。

## 4. 方案决策

采用“完整庭院工作空间模型”。应用维护 `YardWorkspace[]` 与 `activeYardId`，每个工作空间独立持有庭院资料、角色权限、区域、设备、场景、定时和联动。

未采用以下方案：

- 单一状态叠加庭院差异：改动较少，但容易遗漏状态并导致跨庭院数据串用。
- 为每个庭院复制一套页面与数据：初期直观，但代码重复，后续维护成本高。

## 5. 信息架构

### 5.1 庭院选择面板

设备首页顶部的庭院名称是庭院选择入口。点击后打开底部面板，展示用户可访问的庭院。

每个庭院项展示：

- 庭院名称
- 当前用户角色
- 所在地与时区
- 在线设备数与设备总数
- 临时安装商的授权到期时间
- 当前庭院选中标记

面板底部提供三个入口：

- 新建庭院
- 加入庭院
- 管理当前庭院

### 5.2 庭院管理

庭院管理页包含：

- 庭院资料：名称、所在地、时区
- 区域管理：新增、重命名、排序、删除空区域
- 成员与权限
- 临时安装商授权及有效期
- 设备、场景、定时和联动数量概览
- 退出庭院，仅普通成员和临时安装商可见

本阶段不提供“删除庭院”和“转让所有权”。

### 5.3 “我的”页面关联入口

“我的”页面保留“家庭与成员”“庭院时区”等入口，但内容读取当前庭院。用户从这些入口进入时，落到同一套庭院管理子页面，避免形成重复功能。

## 6. 核心交互流程

### 6.1 切换庭院

1. 用户在设备首页点击顶部庭院名称。
2. 底部面板展示所有可访问庭院。
3. 用户选择另一个庭院。
4. 系统更新 `activeYardId` 并关闭面板。
5. 顶部名称、区域筛选和设备列表立即更新。
6. 场景、定时、联动和“我的”页面随后读取同一活动庭院的数据。
7. 显示“已切换至〔庭院名称〕”的轻提示。

切换后重置到该庭院上次使用的区域筛选。若没有历史筛选，则使用“全部”。设备开关、自动化启停等状态始终保存在所属庭院中。

正在编辑场景、定时或联动时，不显示庭院切换入口。用户必须先退出编辑，避免把未完成配置写入其他庭院。

### 6.2 新建庭院

采用轻量完整流程：

1. 输入庭院名称。
2. 选择所在地与时区；时区根据所在地给出默认值，并允许手动调整。
3. 选择或输入初始区域。
4. 确认摘要并完成创建。
5. 新庭院成为当前庭院，进入设备首页空状态。

完成后显示已创建的区域和“添加设备”主按钮。场景与自动化 Tab 分别显示对应空状态。

### 6.3 加入庭院

1. 选择“输入邀请码”或“扫描二维码”。
2. 读取邀请并展示庭院名称、邀请人、角色、权限范围和有效期。
3. 用户确认加入。
4. 系统把庭院加入可访问列表，并切换至该庭院。

原型中的扫码入口使用模拟结果，不调用真实相机或后端。

## 7. 预置庭院

### 7.1 我的庭院

- 角色：所有者
- 所在地：上海
- 时区：Asia/Shanghai
- 数据：保留当前原型中的完整设备、区域、场景、定时和联动
- 用途：展示日常业主使用和完整管理权限

### 7.2 父母家

- 角色：普通成员
- 所在地：苏州
- 时区：Asia/Shanghai
- 数据：另一组灯带、庭院门、灌溉设备，以及较少的场景和自动化
- 用途：展示成员控制权限和跨庭院数据隔离

### 7.3 客户庭院

- 角色：临时安装商
- 所在地：杭州
- 时区：Asia/Shanghai
- 数据：以十二路干接点控制器为主，包含部分已配置和未配置通道
- 用途：展示通道设置、设备测试、诊断和授权到期状态

## 8. 权限模型

| 功能 | 所有者 | 普通成员 | 临时安装商 |
| --- | --- | --- | --- |
| 查看与控制设备 | 是 | 是 | 仅授权设备 |
| 执行场景 | 是 | 是 | 只读，不执行 |
| 创建或修改场景 | 是 | 否 | 否 |
| 创建或修改定时、联动 | 是 | 否 | 否 |
| 添加设备 | 是 | 否 | 是 |
| 设置干接点通道 | 是 | 否 | 是 |
| 设备测试与诊断 | 是 | 否 | 是 |
| 修改庭院资料和区域 | 是 | 否 | 否 |
| 管理成员与安装商授权 | 是 | 否 | 否 |
| 退出庭院 | 不适用 | 是 | 是 |

无权限功能的主要入口直接隐藏。若用户通过保留页面状态等异常路径进入，则显示权限提示并返回安全页面。

临时安装商授权到期后，庭院仍显示在列表中，但标记“授权已到期”，不可进入；用户可查看到期说明。

## 9. 数据模型与状态边界

建议的核心数据结构：

```ts
type YardWorkspace = {
  id: string
  profile: YardProfile
  membership: YardMembership
  areas: Area[]
  devices: Device[]
  scenes: Scene[]
  schedules: Schedule[]
  linkages: Linkage[]
  uiState: YardUiState
}

type YardUiState = {
  selectedAreaId: string | 'all'
}
```

应用级状态只保存：

- `yards`
- `activeYardId`
- 当前视觉模式
- 与庭院无关的个人账号设置

页面只从 `activeYard` 读取庭院业务数据。所有修改动作必须显式携带 `yardId`，以降低后续接入真实接口时误写其他庭院的风险。

## 10. 双视觉实现边界

深色版和暖白版共用：

- 庭院数据模型
- 权限判断
- 切换、新建、加入和管理动作
- 表单校验与异常状态
- 路由和返回逻辑

两套视觉分别实现：

- 庭院选择面板
- 庭院管理页
- 新建庭院流程页
- 加入庭院流程页
- 空状态和权限提示页
- 图标、卡片结构、背景、间距、按钮和弹层表现

建议组件命名按视觉前缀区分，例如 `WarmYardSwitcher` 与 `NightYardSwitcher`。不得以只替换颜色变量的方式强行让两套页面共用同一 DOM 结构。这样可保护暖白版的通透、自然、轻盈风格，也可保留深色版的深蓝黑层次和琥珀色强调。

切换视觉模式不会改变 `activeYardId` 或任何庭院业务状态。

## 11. 空状态与异常处理

- 新庭院设备为空：显示庭院名称、区域和“添加设备”主按钮。
- 新庭院场景为空：显示创建首个场景入口。
- 新庭院自动化为空：分别提供创建定时和创建联动入口。
- 邀请码无效：保留输入内容并提示重新检查。
- 邀请码过期：显示过期原因和请求新邀请的说明。
- 已加入庭院：提示已存在，并提供直接切换入口。
- 删除非空区域：阻止删除，提示先移动该区域中的设备。
- 时区修改：提示现有定时将按新时区执行，确认后再保存。
- 授权过期：禁止进入客户庭院，仅允许查看到期信息。

## 12. 功能验证与验收

本阶段进行功能与状态验证，不代替用户的视觉验收。

功能检查包括：

- 三个预置庭院可以相互切换。
- 四个主 Tab 始终读取同一个活动庭院。
- 设备、区域、场景、定时和联动不会跨庭院串用。
- 新建庭院完成后进入正确的空状态。
- 加入庭院的正常、无效、过期和重复加入状态可到达。
- 三种角色的入口与操作权限符合权限表。
- 深色版和暖白版具备相同功能流程。
- 切换视觉模式后保持当前庭院和业务状态。

视觉验收由用户完成，重点检查两套视觉是否分别符合既定设计语言，而不是彼此迁就。

## 13. 完成标准

- 庭院名称入口可以打开对应视觉风格的选择面板。
- 庭院切换会完整更新所有庭院相关页面和状态。
- 新建、加入、管理和区域管理流程可以从入口走到完成状态。
- 三个预置庭院表现出清晰的数据和权限差异。
- 两种视觉使用独立页面呈现，但不存在业务行为差异。
- 不出现跨庭院状态污染，也不开放本阶段非目标中的高风险操作。
